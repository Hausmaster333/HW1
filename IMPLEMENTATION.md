# ДЗ-1: устройство реализации

Статус: UnqPtr, ShrdPtr, WeakPtr, Sequence на этих указателях, функциональные и нагрузочные
тесты реализованы. Интерфейс по условию сдачи не требуется. MemorySpan и MsPtr не делаются.

## Правила владения

| Событие | UnqPtr<T> | ShrdPtr<T> |
|---|---|---|
| Создание | `make()` — одно выделение под объект | `make()` — одно выделение: блок со счётчиком и объект внутри |
| Копирование | Запрещено; независимая копия только через `clone()` | Новый владелец того же объекта, счётчик +1 |
| Перемещение | Передача владения, источник пуст | Передача владения, счётчик не меняется |
| reset / уничтожение | Сразу удалить объект | Счётчик −1; последний владелец удаляет объект, блок живёт, пока на него смотрят WeakPtr |
| Изменение объекта | Не влияет на результат `clone()` | Видно всем копиям |

Модель совпадает с `std::unique_ptr` / `std::shared_ptr`. Отличия от таблицы в PDF
осознанные: ShrdPtr не ссылается на UnqPtr (это лишний переход по памяти и «уникальный»
владелец, который на деле общий), а UnqPtr не копирует объект неявно (неявная копия
`UnqPtr<Base>` срезала бы объект наследника). Общее владение получается односторонней
передачей: `ShrdPtr<T>(std::move(unique))`, после неё UnqPtr пуст.

## Хранение

`UnqPtr<T>` хранит только `T*` — 8 байт, как `std::unique_ptr`. Удаление — `delete ptr`.
`UnqPtr<T[]>` хранит адрес и длину, удаляет через `delete[]`.

`ShrdPtr<T>` хранит адрес объекта и указатель на блок — 16 байт, как `std::shared_ptr`.
Блок (`ControlBlock`) содержит два 32-битных счётчика — владельцев и слабых ссылок, как
в libstdc++, — и виртуальный `destroy_object()`. Наследники блока знают, как был создан объект:

- `InplaceBlock<U>` — объект лежит в самом блоке, его создаёт `make()`: одно выделение
  (24 байта для `int`, столько же, сколько у `std::make_shared`). Поле — сырая память
  под `U`, а не `U`: объект уничтожается раньше блока, если остались WeakPtr;
- `PointerBlock<U>` — объект пришёл из `UnqPtr<U>`, `destroy_object()` делает `delete`;
- `ArrayBlock<U>` — массив из `UnqPtr<U[]>`, `destroy_object()` делает `delete[]`.

`ShrdPtr<T[]>` хранит блок, адрес и длину, поэтому доступ к элементам не идёт через блок.

## WeakPtr

`WeakPtr<T>` — невладеющая ссылка на объект ShrdPtr (16 байт: блок и адрес). Объект он не
держит, но знает, жив ли объект: блок удаляется только после последней слабой ссылки.
Все владельцы вместе держат одну слабую долю, поэтому блок и объект освобождаются так:

- последний ShrdPtr: `destroy_object()`, затем снимает общую слабую долю;
- последняя слабая ссылка (или эта доля): `delete` блока.

Доступа к объекту напрямую нет, только `lock()`: он возвращает нового владельца или пустой
ShrdPtr. Счётчик увеличивается через `compare_exchange` и только если он не 0 — простой
`fetch_add` мог бы «оживить» объект, который другой поток уже удаляет. `expired()` и
`use_count()` в многопоточной программе — моментальные снимки, решает только `lock()`.
`WeakPtr<T[]>` не сделан: массиву обратные ссылки не нужны.

WeakPtr нужен, где ShrdPtr образовал бы цикл (ребёнок → родитель) или ссылка не должна
владеть (прошивка дерева, перечислители).

## Ключевые методы

Все присваивания устроены одинаково: из источника строится временный указатель, затем
`swap`, затем временный уничтожается вместе с прежним объектом. Так безопасны `a = a`,
`a = std::move(a)` и случай, когда источник лежит внутри удаляемого объекта
(`head = std::move(head->next)`, `head = head->next`).

`reset()` сначала обнуляет поля, потом удаляет объект: если деструктор объекта обратится
к своему владельцу, он увидит пустой указатель, а не висячий адрес.

`ShrdPtr(UnqPtr&&)` выделяет блок до того, как забрать объект у UnqPtr: при `bad_alloc`
объект остаётся у прежнего владельца (строгая гарантия).

`a == b` у ShrdPtr сравнивает объекты (в том числе `ShrdPtr<Derived>` с `ShrdPtr<Base>`),
пустые равны. `static_pointer_cast<Derived>(base)` — новый владелец того же объекта с типом
наследника, как `static_cast` и `std::static_pointer_cast`: без проверки типа.

Публичного конструктора из сырого `T*` нет: фабрика исключает два владельца одного адреса.
`get()` возвращает заимствованный адрес. Для пустого указателя `get()` — nullptr,
`bool` — false, `use_count()` — 0, разыменование бросает `std::logic_error`, выход за
границы массива — `std::out_of_range`. Массив нулевой длины — пустой указатель без
выделений памяти.

## Наследование

Ограничения проверяются при компиляции (`enable_if`, type traits), а не во время выполнения:

- `UnqPtr<Derived>` → `UnqPtr<Base>` разрешено, только если у `Base` виртуальный
  деструктор: иначе `delete Base*` не вызвал бы деструктор Derived. У `std::unique_ptr`
  здесь неопределённое поведение, у нас — ошибка компиляции;
- `ShrdPtr<Derived>` → `ShrdPtr<Base>` и `ShrdPtr<Base>(UnqPtr<Derived>&&)` работают и без
  виртуального деструктора: блок создан для настоящего типа и удаляет именно его;
- обратное преобразование, преобразование между несвязанными типами, снятие `const`
  и ковариантность массивов (`UnqPtr<Base[]>` из `UnqPtr<Derived[]>`) запрещены;
- при множественном наследовании адрес базовой части смещает сам язык при `Derived*` →
  `Base*`, удаление при этом идёт по исходному адресу через блок или виртуальный деструктор.

`clone()` доступен, только если тип копируемый и за `T*` не может прятаться наследник:
тип не полиморфный или `final`. Поэтому «clone после приведения к Base» не компилируется,
а не бросает исключение во время выполнения. `UnqPtr<T[]>::clone()` требует копирующего
присваивания элементов.

Циклы сильных ссылок не собираются: их нужно разрывать явно или делать одну из связей
WeakPtr (тесты показывают удержание объектов циклом, разрыв и цикл через WeakPtr).

## Потоки

Счётчики владельцев и слабых ссылок — `std::atomic<uint32_t>` (у `std::shared_ptr` в libstdc++
тоже 32 бита: блок меньше, копирование не медленнее std), поэтому копии одного
объекта можно создавать и отпускать из разных потоков:

- увеличение — `fetch_add(relaxed)`: копия делается из живого владельца, объект уже
  существует, синхронизировать нечего;
- уменьшение — `fetch_sub(acq_rel)`: release публикует записи потока в объект, acquire у
  последнего владельца делает их видимыми до вызова деструктора;
- если перед уменьшением владелец один и WeakPtr нет (оба счётчика равны 1, чтение с
  acquire), скопировать или оживить объект больше некому: блок удаляется без lock-инструкции. Так же
  устроен `_M_release` в libstdc++; без этого наше освобождение было на 3 нс медленнее STL.

Потокобезопасен только счётчик. Одновременная запись в один и тот же экземпляр ShrdPtr из
разных потоков — гонка, как и у `std::shared_ptr`; доступ к самому объекту синхронизирует
пользователь. `use_count()` в многопоточной программе — лишь моментальный снимок.

Цена атомарности — инструкция с префиксом `lock` на каждое копирование и освобождение
(несколько наносекунд даже без конкуренции потоков).

## Sequence

`sequence/` — Sequence, ArraySequence, ListSequence, mutable / immutable варианты,
map / where / concat / slice и IEnumerator из LR-2, переведённые на свои указатели.
Mutable `append` / `prepend` / `insert_at` меняют объект и возвращают ссылку, Immutable —
возвращают `UnqPtr<Derived>` с новой копией. `map`, `where`, `concat`, `slice`,
`get_sub_sequence` возвращают `UnqPtr<Sequence<T>>`.

`DynamicArray` хранит буфер в `UnqPtr<T[]>`; `resize()` заполняет новый буфер отдельно и
подменяет его только после успешного копирования. Узлы `LinkedList` владеют следующими
через `ShrdPtr<Node>`, хвост — невладеющий `WeakPtr<Node>`, длинная цепочка освобождается
итеративно. Сырых адресов из умных указателей контейнеры не берут: перечислитель массива
читает через `get()` по ссылке на массив, перечислитель списка держит текущий узел через
`ShrdPtr`. Перечислитель держит `ShrdPtr<IteratorState>` с признаками `alive` и `version`:
после изменения или уничтожения контейнера он бросает `std::logic_error` вместо чтения
освобождённой памяти.

## Тесты

`mingw32-make check`: 73 теста указателей и 42 теста Sequence.

Утечки: `support/alloc_counter.cpp` подменяет глобальные `operator new` / `delete`, а
`tests/leak_check.cpp` после каждого теста сверяет число живых выделений. Проверка сама
проверена: тест с забытым `delete` и тест с циклом ShrdPtr падают. В тестах счётчики
выделений атомарные (память выделяют и рабочие потоки), в бенчмарке — обычные
(`-DALLOC_COUNTER_SINGLE_THREAD`): атомарные добавляли ~5 нс к каждому `new`. Тот же счётчик умеет
заставить N-е выделение бросить `bad_alloc`; тесты `FaultInjectionTest` повторяют
операцию с отказом на каждом выделении по очереди и после каждого отказа проверяют
утечки и целостность контейнера.

Что проверяется помимо основных операций:
- при компиляции — размеры указателей, `noexcept` перемещений, запреты копирования UnqPtr,
  неверных преобразований, владения сырым адресом, доступность `clone()`;
- самоприсваивание копированием и перемещением; присваивание из объекта, который
  удаляется этим же присваиванием; повторный вход в `reset()` из деструктора объекта;
- исключение конструктора и нехватка памяти в `make()`, частично выполненный `clone()`
  массива, отказ выделения блока при передаче из UnqPtr;
- число выделений: `make()` — одно, копия ShrdPtr и пустые операции — ноль;
- WeakPtr: объект умирает с последним владельцем, а блок — с последней слабой ссылкой
  (по счётчику выделений); `lock()` после удаления пуст; разрыв цикла; объект со слабой
  ссылкой на себя; 8 потоков делают `lock()`, пока последний владелец отпускает объект;
- потоки: 8 потоков одновременно копируют и отпускают один объект — счётчик сходится
  (с неатомарным `++`/`--` тест падает: `use_count` 4–6 вместо 1); последний владелец в
  любом потоке удаляет объект один раз и видит записи всех потоков;
- множественное наследование без виртуального деструктора, циклы ссылок,
  массивы нулевой длины, индексы `size()` и `SIZE_MAX`, невыполнимый размер массива.

На Linux `make valgrind` дополнительно прогоняет тесты под Valgrind, кроме двух: `ImpossibleSizeThrows`
(Valgrind считает ошибкой сам запрос гигантского размера) и `WeakPtrThreadTest` (Valgrind выполняет
потоки по очереди, и цикл ожидания старта растягивает тест на часы).

## Бенчмарки

`mingw32-make benchmark`, затем `python benchmarks/run.py` (нужен matplotlib).
Каждый замер — отдельный процесс, N = 10 … 10^8, медиана повторов. Варианты:
raw (сырой указатель с ручным `new` / `delete`), std (STL), custom (наши).

| Сценарий | Что измеряется |
|---|---|
| unique | N независимых владельцев: создание, чтение всех, освобождение |
| shared | N объектов в общем владении: то же |
| copy | N ссылок на один объект: копирование, чтение, освобождение |
| move | передача владения N объектами из одного массива в другой |
| list | односвязный список из N узлов: построение, обход, разрушение |

Память считается двумя способами: точные байты кучи по счётчику выделений плюс `sizeof`
указателя и фактический прирост рабочего набора процесса (с накладными расходами
аллокатора). Результаты: `benchmarks/results/report.md`, `batch.png`, `totals.png`,
`time.png`, `overhead.png`, `memory.png`, `summary.csv`, `samples.json`. Текст выводов,
который попадает в отчёт, лежит отдельно в `benchmarks/notes.md`.

Размеры кэшей L2 и L3 benchmark спрашивает у ОС (`GetLogicalProcessorInformation` на
Windows, `/sys/devices/system/cpu` на Linux) для того ядра, на котором идёт замер, и
пишет в каждый замер. Описание машины тоже сохраняется в `samples.json`, поэтому
`run.py --from-samples` на другом компьютере перестраивает отчёт с данными машины замера.
